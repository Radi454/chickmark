# ChickMark AI Agent Harness Design

Date: 2026-07-28

## Status

Approved in conversation for specification. This design supersedes the
fixed-routing and scripted-conversation parts of the 2026-07-27 Telegram
Hatchery Agent design. It retains that design's verified webhook, durable
evidence, admin review, security, and audit-trail requirements.

## Goal

Make ChickMark's Telegram bot a genuine AI agent that can:

1. Hold a natural Arabic, English, or mixed-language conversation in response
   to any allowed user's message.
2. Answer authorized questions about the user's customer, flocks, station
   records, trends, comparisons, and warnings.
3. Detect from conversation that the user may want to enter data, ask for
   confirmation, and then guide the user through the applicable station or
   module without relying on fixed trigger phrases or scripted dialogue.
4. Collect and organize validated station data, show one complete station
   summary, and submit the confirmed station to admin review.

The AI owns interpretation, conversational decisions, question wording, and
normal customer-facing responses. Backend code is a deterministic harness for
authorization, tool execution, schema validation, calculations, state,
idempotency, evidence, and safe persistence.

## Product Principles

- Every authorized message reaches the AI agent. There is no greeting list,
  keyword trigger, or fixed conversational router in front of it.
- Normal replies are generated by the AI from the current conversation and
  tool results. Backend code does not assemble normal customer-facing scripts.
- The AI never receives raw database credentials and never executes SQL.
- The AI may propose only typed tool calls exposed by the harness.
- The backend is authoritative for access, validation, calculations, and
  writes. The model cannot override those rules.
- The AI asks only when context, intent, or required data is missing,
  conflicting, invalid, or uncertain.
- Valid progress is retained without asking for confirmation after every value.
- Each completed station receives one versioned summary and one user
  confirmation before it can enter admin review.
- No Telegram conversation writes directly to final operational records.

## Actors and Authorization

### Normal Telegram user

An admin approves the Telegram user in ChickMark's Agent screen and assigns the
user to exactly one customer account. Every read tool and write tool is scoped
to that customer by the backend. The AI cannot request or reveal another
customer's data.

### ChickMark admin

The admin user may access all customers. If a question or intake does not
identify a customer clearly, the AI may infer one from context or ask the admin
to choose. Admin scope is still enforced by the backend rather than trusted
from the model.

### Unapproved, pending, or revoked Telegram user

These users do not reach the AI agent. Access denial, pending approval, and
revocation are security states and may use short deterministic system messages.

## Selected Architecture

Use one unified tool-calling AI agent behind the verified Telegram webhook.

The selected approach replaces the current combination of:

- an AI interpreter,
- a hardcoded conversational phrase classifier,
- a legacy open-question interceptor, and
- separate scripted workflow replies.

For each authorized inbound turn, the harness sends the AI:

- the new message and any attachment context,
- recent conversation turns,
- the active intake state, if any,
- the user's enforced customer scope,
- the relevant sector and station catalog metadata,
- unresolved legacy-draft context when relevant, and
- the typed tools available for that user and state.

The AI can respond conversationally with no tool call, call one or more tools,
or ask a natural clarification. Tool results are returned to the same agent so
it can explain them naturally. A bounded loop prevents unlimited tool calls in
one Telegram turn.

The backend never runs a second phrase classifier after the AI has interpreted
the message. An AI decision that a message is ordinary conversation remains
ordinary conversation.

## Why This Approach

### Selected: unified tool-calling agent

This approach gives the AI control of the conversation while keeping data and
authorization deterministic. New stations add schemas and tools, not new
conversation branches.

### Rejected: AI router followed by scripted workflows

This is close to the current implementation. It improves classification but
still produces mechanical dialogue and creates conflicts when fixed routing
disagrees with the model.

### Rejected: autonomous AI with direct database access

This is flexible but unacceptable for customer isolation, reliable validation,
auditing, and production safety.

## Tool Families

Tool outputs are structured data. Except for security and infrastructure
failures, tools do not provide final customer-facing message text.

### Identity and scope tools

- `get_user_scope`
  - Returns whether the user is admin and the customer IDs the backend permits.
  - Normal users always receive exactly one customer.
- `get_customer_context`
  - Returns safe customer identity and configured sector information.

### Flock and operational read tools

- `list_customer_flocks`
  - Lists authorized flocks with status, breed, age context, and important
    dates.
- `get_flock_context`
  - Returns the authorized flock profile and current audit context.
- `query_station_records`
  - Returns bounded, filtered station records for an authorized flock and date
    range.
- `compare_station_metrics`
  - Runs deterministic ChickMark calculations for comparisons, trends, and
    warnings.
- `get_record_provenance`
  - Returns the customer, flock, station, record date, and freshness metadata
    needed to explain an answer.

The AI can combine stored facts with deterministic comparisons and warnings. It
must identify the relevant customer, flock, station, and date in its answer. It
must say when data is missing or outdated and must not estimate missing
operational values.

### Catalog and schema tools

- `list_applicable_stations`
  - Returns the current catalog filtered by the assigned customer's sector and
    the user's permissions.
- `load_station_schema`
  - Returns the selected station's versioned fields, units, validation,
    dependencies, calculations, aliases, and persistence mapping.

### Intake tools

- `start_intake`
  - Starts a versioned working session only after the user confirms the AI's
    interpretation that data entry is intended.
- `record_station_values`
  - Proposes normalized values with their source phrases and confidence.
  - The backend accepts valid values and returns validation results for rejected
    or uncertain values.
- `get_intake_status`
  - Returns accepted values, missing fields, unresolved clarifications, and
    station completeness.
- `create_station_summary`
  - Produces an immutable, versioned snapshot from validated values and
    deterministic calculations.
- `confirm_station_summary`
  - Accepts confirmation only for the exact current summary version.
- `submit_station_for_review`
  - Creates or updates a pending admin-review record. It never creates the final
    operational record.
- `pause_intake`, `resume_intake`, and `cancel_intake`
  - Manage user-controlled session state without losing audit evidence.

## Station Schema Registry

The station registry is the canonical contract between the AI harness and
ChickMark's operational model. It is derived from current app logic and
database mappings but includes semantics that raw database introspection cannot
provide.

Each station schema contains:

- sector key,
- module and station key,
- localized display names and natural-language aliases,
- schema version,
- required and optional fields,
- field type and unit,
- valid range or allowed choices,
- dependencies between fields,
- explicit-zero rules,
- deterministic calculations,
- completion rules,
- database table and column mapping,
- read/query dimensions and measures, and
- any admin-review warnings.

Adding or changing a station updates the registry and schema version. It does
not add greeting rules, intent keywords, question order code, or fixed reply
templates.

The first existing conversational schema, `chicks.pasgar@1`, becomes one entry
in this registry rather than a special conversation controller.

## Natural Conversation Behavior

### Ordinary conversation

Any allowed message is interpreted by the AI. Greetings, incomplete phrases,
questions, misspellings, and colloquial Arabic remain normal conversation
unless the model has evidence that a tool is needed.

### Possible data-entry intent

There is no fixed phrase such as "enter data." When the AI infers that the user
may want to record operational data, it asks a natural confirmatory question.
No intake is created before the user confirms.

### Station selection

After confirmation, the AI calls `list_applicable_stations` and presents the
sector-filtered catalog naturally. The user may choose by number, canonical
name, alias, or ordinary language. The backend resolves only catalog entries;
an uncertain match causes the AI to clarify.

### Data collection

The AI loads the selected schema and organizes the questions based on what the
user has already supplied. The user may:

- provide one value,
- provide several values in any order,
- provide all values in one message,
- correct an earlier value,
- use Arabic, English, or mixed language,
- attach a supported photo, PDF, spreadsheet, or file, or
- interrupt the intake with an ordinary question.

Valid values are recorded silently. The AI asks one focused clarification when
a value is missing, ambiguous, conflicting, invalid, or below the confidence
threshold. It does not force the user through a fixed field order.

### Summary and multiple stations

When the selected station is complete, the AI presents one localized summary
containing every validated input and calculated result. The user may confirm or
correct it. Confirmation applies only to the displayed summary version.

After confirmation, the AI asks naturally whether the user wants to add another
applicable station to the same audit visit or finish. Every confirmed station
is submitted to admin review; no final operational save occurs from Telegram.

## Database Question Answering

The same agent answers questions about the authorized customer's flocks and
records.

Examples include:

- current flock profile and age context,
- latest station values,
- hatchability or quality results,
- changes over time,
- comparisons between authorized flocks,
- comparisons with stored benchmarks, and
- current warnings or missing evidence.

The AI decides which read tools to call. The backend:

- injects customer filters rather than accepting model-provided unrestricted
  filters,
- bounds date ranges and row counts,
- exposes only approved fields,
- calculates metrics using ChickMark's deterministic formulas, and
- returns provenance and freshness metadata.

The AI may summarize and explain those results but may not invent a record,
metric, comparison, or date.

## Conversation and Intake State

Durable state includes:

- authorized Telegram user and customer scope,
- recent conversation context,
- active audit visit,
- selected sector/module/station,
- station schema key and version,
- accepted working values,
- source phrases and confidence,
- pending clarification,
- summary snapshot and version,
- user confirmation evidence,
- tool calls and validation results, and
- pending admin-review identifiers.

Conversation turns and tool evidence remain auditable. Long-term conversational
memory is bounded to operationally relevant context; the agent does not need
unlimited chat history.

## Backend Harness Responsibilities

The harness is deterministic and is responsible for:

- Telegram webhook authentication,
- staff approval and customer authorization,
- duplicate-update protection,
- conversation and intake state,
- tool availability by role and state,
- parameter and schema validation,
- customer-scoped database access,
- deterministic calculations,
- attachment loading and bounded extraction,
- persistence and audit evidence,
- summary-version enforcement,
- admin-review submission, and
- rate, timeout, and tool-loop limits.

It is not responsible for:

- recognizing greetings,
- enumerating conversational phrases,
- deciding question wording,
- enforcing a fixed question order,
- generating normal success messages, or
- selecting a workflow through keyword matching.

## Errors and Fallbacks

- AI provider unavailable: preserve state and send a short infrastructure retry
  message. Never fall back to a legacy form or reinterpret the message as data.
- Tool validation failure: return the structured failure to the AI so it can
  ask a focused clarification.
- Unauthorized customer or flock: deny the tool call without revealing whether
  the target exists.
- Missing or stale database evidence: return explicit provenance status and let
  the AI explain the limitation.
- Unreadable attachment: preserve the source reference and let the AI request a
  clearer file or typed values.
- Duplicate Telegram update: acknowledge idempotently without another AI call,
  write, or reply.
- Conflicting simultaneous updates: use session versioning and retry safely.
- Tool-loop or model timeout: stop the turn, retain durable progress, and send a
  bounded retry response.

Deterministic customer-facing messages are limited to access control, revoked or
paused service state, and infrastructure failure where the AI cannot respond.

## Security

- The Telegram bot token, AI credentials, and service-role credentials remain
  server-side secrets.
- The AI receives no database credentials.
- Normal-user tool calls are always bound to the customer assigned in the
  Agent screen.
- Admin access to all customers is verified by backend authorization.
- Read tools expose an allowlisted projection rather than arbitrary SQL.
- Write tools accept only fields declared by the selected schema version.
- Tool outputs and attachment contents are untrusted data and cannot change
  system instructions or tool policy.
- Prompt injection cannot grant tools, broaden customer scope, bypass summary
  confirmation, or write final records.
- Final admin approval remains authenticated, backend-enforced, and auditable.

## Migration from Current Behavior

The change is additive and staged:

1. Introduce the unified agent protocol and generic schema registry alongside
   current tables.
2. Adapt the existing Pasgar schema and durable intake state to the generic
   tool contract.
3. Route every authorized text turn through the unified agent.
4. Remove hardcoded conversational classification and prevent legacy open
   questions from intercepting agent turns.
5. Expose legacy drafts only through explicit agent tools and context.
6. Add remaining station schemas and read mappings incrementally.
7. Retire obsolete scripted reply and legacy routing code after transcript and
   production verification.

Existing submissions, drafts, confirmed intakes, and audit evidence are
preserved.

## Observability

For each turn, record:

- user and enforced customer scope,
- model and schema version,
- selected tool names,
- validated tool arguments,
- tool duration and result status,
- state version before and after,
- generated reply delivery status, and
- rejection or clarification reasons.

Logs must not expose secrets or unnecessary customer data. Metrics should track
tool errors, clarification frequency, model failures, response time,
cross-customer authorization denials, and fallback usage.

## Testing Strategy

Tests evaluate intent, tool selection, safety, and factual correctness rather
than exact customer-facing wording.

### Conversation transcripts

- Arabic, English, and mixed-language conversations.
- Colloquial Arabic, misspellings, fragments, greetings, and previously unseen
  phrasing.
- Ordinary chat during active and legacy drafts.
- Natural detection and confirmation of possible data-entry intent.
- Station selection by name, number, alias, and contextual description.
- Multiple values in any order and corrections before confirmation.
- Multiple stations in one audit visit.

### Schema contracts

- Every active sector station has a versioned registry entry.
- Required fields, ranges, units, dependencies, calculations, completion, and
  persistence mappings are valid.
- Flutter and backend calculations produce the same result.
- A schema change requires a new version and does not invalidate older evidence.

### Authorization and security

- A normal user can read and write only the assigned customer's data.
- Admin can access all customers.
- Unauthorized IDs do not leak existence.
- Prompt injection cannot expand tools or scope.
- Anonymous, pending, and revoked users never reach the AI.
- Telegram, AI, and database secrets never appear in prompts or logs.

### Database answers

- Facts match stored records exactly.
- Comparisons, trends, warnings, and benchmarks match deterministic
  calculations.
- Answers include customer, flock, station, record date, and freshness context.
- Missing and stale data are reported explicitly rather than estimated.

### Reliability

- Duplicate updates produce no duplicate AI call, reply, or write.
- Interrupted sessions resume with the same accepted values.
- AI and tool failures preserve progress.
- Summary corrections create a new version.
- Only the current confirmed summary enters admin review.
- Confirmed review records never become final without admin approval.

## Acceptance Criteria

The design is implemented when:

1. No authorized conversational message is classified by a hardcoded phrase or
   keyword list.
2. One unified agent decides whether to chat, read data, clarify, or request an
   intake tool.
3. Normal users are restricted to their one Agent-screen-assigned customer;
   admin can access all customers.
4. The AI can answer factual and analytical questions about authorized flock
   data with provenance and freshness context.
5. Possible data entry is recognized from natural language and confirmed
   before an intake begins.
6. Applicable stations are loaded dynamically from the sector-filtered schema
   registry.
7. The AI collects station data without a fixed question order and asks only
   focused clarifications.
8. Each completed station receives one versioned user-confirmed summary and is
   sent to admin review.
9. Multiple stations can be added to the same audit visit.
10. Existing legacy drafts cannot intercept ordinary agent conversation.
11. Security, transcript, schema, factual-answer, and reliability tests pass.

## Out of Scope

- Direct AI access to SQL or database credentials.
- Automatic final operational writes without admin approval.
- Unlimited general-purpose conversation unrelated to ChickMark operations.
- Cross-customer access for normal users.
- Replacing deterministic ChickMark calculations with model arithmetic.
- Using raw database introspection as the complete station schema.
